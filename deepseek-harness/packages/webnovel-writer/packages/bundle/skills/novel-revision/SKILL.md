# 改稿（Novel Revision）

本技能把审核记录里已授权的处置，落实为新一版待审稿。

- 改写执行者是**改稿子代理**。主控绝不亲自写正文。
- 唯一例外见「小修快路」：作者逐字给出的替换或明确的删除，主控原样转交工具，不自行改写。
- 人设与工序在包内 `底本/改稿章程.md`。派发时把全文放进任务包。
- 派发使用 `novel_delegate`，传 `role: revision`。运行时只向该实例注入改稿规约和只读权限，整稿与映射交回主控；已授权处置和改稿章程仍须完整交接。

## 范围：只改草稿区

本技能只处理**草稿区范围内的修改**。

1. 发现项的 `影响范围` 带以下任一个词时，一律走提案呈报上游：
   `世界书`、`大纲`、`作品契约`、`构想`、`账本`、`本书记忆`。
2. 作者对这类条目说「保留／驳回／无法判断」时，可以用**纯处置批**记入审核记录。
   - 纯处置批不带新稿正文，也不带补丁。
   - 实际的上游修改仍然只走提案。不得借审读回写工具直接设置「已转提案」。
3. 提案经作者通过后（`novel_resolve_proposal` 决定为「通过」），原发现项记 `已转提案`：
   - 用纯处置批，传 `提案编号: NNNN`，改动说明写转交原因。
   - 提案登记时必须提供 `关联发现项`（卷、章、章名、发现项编号）。工具核对关联身份及「已通过」状态，否则拒绝。
   - 上游改动若影响本章正文，按当前材料重跑《全面审读》。
4. 带新稿或补丁的批次里混进一条上游条目时，工具拒绝整批，报「须呈报上游」。
   - 所以先按影响范围分组，再派改稿。
   - 这样不会在改完稿后才发现整批不可写入。

旧版插件读取转交记录时显示「待处理」，不会自动算作审核完成。转交信息仍保留在记录中；需要继续该流程时使用支持转交记录的插件。

## 标准流程

1. **读待处理项**
   - 先调用 `novel_get_story_status`，取本章 `审核记录哈希`。
   - 再读审核记录 `草稿区/审核/卷<NN>-<章名>.json` 中「待处理」的发现项。
   - 需要的字段：`发现项编号`、证据位置、问题说明、修改建议、影响范围。
   - 核对每条编号非空，且互不重复。
   - 编号原样取自 `novel_record_review_findings` 的返回或当前审核记录，不缩写模块名、不按印象拼接。多个模块回写后重取最新 `审核记录哈希`，不要沿用先前模块的旧哈希。
   - 编号为空时，回《全面审读》按模块名重新回写补号，再继续。
   - 原因：用空号批量落实时，一条处置会套到所有同号条目上。

2. **汇总处置决定**：逐条确定处置。

   | 处置 | 动作 |
   |---|---|
   | 已解决、已接受修改 | 需要改正文 |
   | 作者保留、已驳回、无法判断 | 只记处置 |

   - 作者已口述改法的条目，把改法原文写进处置清单。

3. **派改稿子代理**（有正文改动时）。任务包包含：
   - `底本/改稿章程.md` 全文；
   - 当前待审稿正文；
   - 已授权的处置清单。每条含 `发现项编号`、证据位置、问题说明、修改建议、作者改法；
   - 硬约束：契约第六分部「创作禁区与不可妥协项」原文，以及确认细纲的 `〔硬〕` 行；
   - 契约「叙事方式与文风基调」分部原文。

   **材料全部内联，不给书仓路径。** 子代理返回**整稿新版**，以及「发现项→改动」映射清单。

4. **批量落实**：调用 `novel_apply_revision_batch`。
   - 参数：卷、章、章名、`新稿正文`、`处置`、`生成模块`。
   - 参数名是 `处置`。传 `处置清单` 时，工具报「处置清单为空」。
   - `生成模块` 必须显式传 `改稿子代理`。缺省时记成 `改稿`。
   - 每次都传上一步拿到的 `审核记录哈希`。成功时返回新哈希，供下一批使用。
   - 哈希不一致、编号未知或同批重复时，工具拒绝整批。先重取状态，再来。
   - 一次调用写出新稿 `稿<N+1>.md`，并回写全部处置。
   - 新稿版本 +1。旧稿降级留档。候选事实段原样带过。

5. **只记处置的批次**
   - 不传新稿正文。
   - 处置里只写编号、处置和必要的改动说明。
   - 其余字段、其他发现项与审核证据，由工具原样保留。
   - 二十条以上的处置也照此一批传。不重传发现项全文。

6. **作者自己改的版本**：用 `novel_import_draft` 导入（角色: 待审稿、生成模块: 作者手改）。处置照常回写。

7. **复审**
   - 正文或审读依据改变时，按当前输入重跑《全面审读》，确认修复没有回归。
   - 只有纯处置、且输入未变时，不为获取相同建议而重审。
   - 全部处置有效、证据适用当前稿、审核完成后，进入定稿准备。

## 小修快路

适用：作者逐字给出新句子，或明确要求删除某一段。作者只给方向（如「改紧凑一点」）时，不走快路，派改稿子代理。

1. 直接调用 `novel_apply_revision`。参数：单条处置，加补丁旧文和补丁新文，`生成模块: 作者手改`。
   - 补丁新文必须是作者给出的原文；删除时为空串。主控不得自行增删字句。
2. 补丁旧文必须在待审稿正文中唯一命中。
3. **补丁只在处置为 `已解决` 或 `已接受修改` 时生效。** 处置为 `待处理` 时传补丁，工具拒绝。

## 重入（轮次推进）

- 每轮「审读→改稿→复审」算一个改稿轮次。轮次随新稿推进 +1。
- **轮次上限 3。** 第 3 轮仍有未解决问题时，不再自动发起新一轮：
  - 向作者标「须作者决定」；
  - 附**瓶颈诊断**：问题集中在哪个维度；根因在草稿还是上游设计；
  - 列出可选出路：接受现状入档、退回上游、作者亲自定夺。
- 上限是建议，不是门禁。**作者要求继续改，就照做。** 不要把上限当作拒绝的理由。
- 作者选「接受现状入档」时，余下条目按作者意见逐条记 `作者保留` 或 `已驳回`，再进定稿准备。
  - 留着「待处理」时，审核判为不完成。
- 轮次按草稿目录里 `生成模块` 为 `改稿子代理`、`改稿` 或 `作者手改` 的稿数计算。润色稿不计入。
- 处置历史以审核记录为准。两者都不凭会话记忆。

## 工件契约

| 工件 | 路径 | 属性 |
|---|---|---|
| 新待审稿 | `草稿区/草稿/卷<NN>-<章名>/稿<N+1>.md` | frontmatter：`角色: 待审稿`，`版本` +1，`父版本`，`生成模块: 改稿子代理`（必须显式传，缺省是 `改稿`） |
| 新待审稿的来源 | 同上 | 批量落实时 `来源快照` 记处置编号。小修快路不记。旧稿改为 `角色: 草稿` 留档 |
| 审核记录 | `草稿区/审核/卷<NN>-<章名>.json` | 机器态 JSON（`schemaVersion: 1`）。处置只经工具回写，不手工编辑 |

## 工具

| 工具 | 何时用 | 不要 |
|---|---|---|
| `novel_apply_revision_batch` | 汇总完一批处置后一次落实（新稿和处置同批） | 传未授权的改动；手工编辑审核记录 |
| `novel_apply_revision` | 作者口述的一处小改；单条纯处置 | 用它做整章重写 |
| `novel_import_draft` | 作者贴自己改过的版本 | 对作者稿再跑润色（作者点名除外） |
| `novel_record_proposal` | 发现项涉及上游真源时，按《工作台总控》“提案与吃书补偿”整理影响面后登记 | 把上游变更混进改稿处置清单 |
| `novel_resolve_proposal` | 作者明确通过或驳回后，回写提案决定 | 把建议当成作者决定 |
| `novel_apply_retcon` | 已定稿内容更正。转《定稿沉淀》完成呈报与本次作者裁决 | 用草稿改稿工具覆盖定稿 |
| 改稿子代理 | 一切判断性的正文改写 | 让主控代写；任务包缺改稿章程 |

## 作者介入

- 作者能做什么：自己动手改（贴整版或局部）；指定某几条按自己的写法改；驳回子代理的改动。
- 用哪个通道：
  - 贴整版：`novel_import_draft`（角色: 待审稿、生成模块: 作者手改）。
  - 指定改法：写进处置清单的 `改动说明`，交改稿子代理执行。
- 主控接到后：
  - 作者手改的稿，照常回写处置，并进入复审。
  - 对 `生成模块: 作者手写/作者手改` 的稿，不主动再改一个字。发现项处置一律呈作者。

## Off-limits

- 真源写入限制不放松。真源修改走提案：影响分析前置，整批确认。
- 处置与改动一一对应。
- 子代理失败只单点重试。严禁主控代写正文。
- 审核记录只经处置工具修改。
  - 工具报「审核记录已变化」时，重取哈希后重试。
  - 不要用通用写工具补写 JSON。
- 改稿不产生 git 提交（草稿区不入库）。
